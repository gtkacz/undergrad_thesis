     #S280 Fix CUDA out of memory error in bilateral blur denoising during grid search (Apr 12, 9:44 PM)


     Investigated: The grid search crashed with CUDA OOM when evaluating DenoiseTransform with template_window_size=11 and search_window_size=15. The error occurred in kornia.filters.bilateral_blur attempting to allocate 2.84 GiB with only 2.66 GiB available on a 15.56 GiB GPU. Examined src/util/preprocessing.py to understand the DenoiseTransform implementation and identified that bilateral blur was processing entire batches without memory management.

     Learned: The bilateral blur operation unfolds input tensors from B×C×H×W to B×C×H×W×K² dimensions, where K is the kernel size. With large batches and large window sizes, the intermediate unfolded tensors exceed GPU memory capacity. The original DenoiseTransform implementation prioritized simplicity over memory efficiency, calling kornia.filters.bilateral_blur directly on full batches without chunking, gradient checkpointing, or other memory optimization strategies. Memory fragmentation (2.34 GiB reserved but unallocated) indicated that GPU memory wasn't being properly released between grid search iterations.

     Completed: Implemented batch chunking in DenoiseTransform.forward() to prevent CUDA OOM errors. Batches larger than 32 images are now split into chunks, processed independently through bilateral blur, and concatenated. This allows grid search to evaluate larger window size combinations without exhausting GPU memory while preserving the original single-pass implementation for smaller batches.

     Next Steps: The grid search can now resume testing the Denoise configuration with previously problematic window sizes. Monitor whether the chunking strategy successfully completes the grid search evaluation and verify that denoising accuracy results are consistent with the unchunked implementation.

  ---
  Pre-submission review: Significance of Transform Ordering and Selection in CNN
  Preprocessing for Binary Skin Disease Classification

  Bottom line

  The manuscript is numerically faithful and statistically honest — every
  headline number I checked against the released analysis.json and against the
  text's own internal cross-references is consistent, and the statistical
  apparatus (multi-seed replication, bootstrap CIs, permutation tests, Holm +
  Benjamini–Hochberg, leave-one-seed-out) is more rigorous and more
  self-critical than the typical preprocessing paper. The novelty claim
  (variance decomposition into selection vs ordering) is genuine.

  It is not ready to send to Elsevier as-is. Two issues will, with high
  probability, draw a major-revision-or-reject from a competent Computers in 
  Biology and Medicine (CBM) referee:

  1. A cross-source confound that the paper does not acknowledge. Healthy and
  diseased images come from different source datasets (diseased = HAM10000;
  "healthy" = some other corpus), so the 98.09% baseline — against which every
  result in the paper is measured — cannot be shown to reflect pathology
  discrimination rather than dataset-source discrimination. This is the textbook
  shortcut-learning failure mode in dermoscopy, and it is not in the
  limitations section.
  2. Accuracy is the only evaluation metric. No AUROC, sensitivity, specificity,
  F1, or calibration metric appears anywhere — below current medical-AI
  reporting norms (CLAIM, TRIPOD+AI), and conspicuous given that the paper's own
  error-mechanism section is about the false-positive/false-negative trade-off.

  Separately, when a referee downloads the advertised replication code, they
  will find that two of the four transforms are not the methods the paper 
  describes, and a third is cited to the wrong algorithm variant. All of this is
  fixable; none of it is fatal to the underlying empirical finding. Details
  below, organized to your three questions.

  ---
  Part 2 — Does it make sense to send to Elsevier / CBM?

  Scope fit: yes, with direct precedent. CBM has published the single closest
  prior-art paper you cite (Rodrigues et al., Comput. Biol. Med. 2020, on
  preprocessing-vs-CNN for HEp-2 cells). A combinatorial preprocessing study
  with a strong statistical core is squarely in scope. The methodology exceeds
  the rigor of typical CBM preprocessing papers, and the selection-vs-ordering
  variance decomposition is, to my knowledge, unprecedented in this literature —
  the adjacent work (AutoAugment/RandAugment; FreeAugment, ECCV 2024) concerns
  training-time stochastic augmentation policy search, not deterministic
  preprocessing-ordering with variance decomposition. The "to our knowledge, no
  prior work has decomposed… selection and ordering" claim is defensible; I
  would keep the hedge and, if anything, cite FreeAugment to pre-empt the
  obvious "isn't this AutoAugment?" referee.

  Why it is not yet submittable to CBM specifically:

  1. The confound + provenance issue (Part 1). A near-ceiling 98% cross-source
  result with no shortcut-learning control and an internally inconsistent
  description of the negative class is the kind of thing that triggers a
  desk-adjacent major revision at a biomedical venue. CBM referees will expect
  shortcut learning to be addressed explicitly.
  2. Accuracy-only metrics. For a binary medical classifier, reporting only
  accuracy (even decomposed into ΔFP/ΔFN) is below CLAIM/TRIPOD+AI expectations.
  The irony is that you already computed the confusion matrices, so
  sensitivity, specificity, F1, balanced accuracy, and MCC are derivable from 
  existing artifacts with no retraining. AUROC needs per-image probabilities,
  which §V.E says were not persisted for all runs — so AUROC is achievable at
  least for seed 42 now, and fully on a re-run.
  3. Methods-vs-code mismatches (items A–C, G). Because the paper stakes its
  credibility on open replication (§Data availability advertises full code
  release), a referee who runs the code and finds that "Non-Local Means" is
  bilateral filtering and that Table 1's normalization parameters can't come
  from the stated grid will lose confidence in the whole methods section.
  Individually minor; collectively a MAJOR accuracy problem precisely because
  the code is public.

  Journal recommendation. If the goal is the strongest possible paper, fix the
  confound and add clinical metrics and keep CBM — the precedent and the
  methodological rigor genuinely fit. If you would rather not run a new control
  experiment, the contribution is fundamentally methodological (how to
  construct/evaluate preprocessing pipelines), and Biomedical Signal Processing 
  and Control (Elsevier; already your most-cited venue in the related work) is a
  more natural home for a methods contribution where the dataset confound,
  while still a weakness to disclose, sits against a slightly lower
  clinical-validity bar. Computer Methods and Programs in Biomedicine is a
  reasonable third option. I would not soften the confound disclosure in either
  case.

  Part 3 — Prioritized improvements

  Blockers (before any submission):

  1. Resolve the negative-class provenance and the source confound. State
  exactly where the healthy images come from; fix the DERM12345
  mischaracterization (it has no healthy class); remove or correct the orphan
  megpaulson_healthy_skin/HealthySkin entries. Then add a shortcut-learning 
  probe — at minimum, a low-level baseline (e.g., a colour-histogram or mean-RGB

  signature is demonstrably doing the work and the framing must change
  accordingly. Ideally, add a within-source control (both classes from the same
  acquisition source, e.g., benign vs malignant within one corpus) or a
  source-stratified analysis. Either way, add the confound to §V.E explicitly.
  2. Add threshold-independent and per-class metrics. Sensitivity, specificity,
  F1, balanced accuracy, and MCC are computable now from the confusion matrices
  you already have; add AUROC for seed 42 (and for all seeds on any re-run).
  Frame the reporting against CLAIM/TRIPOD+AI. This also strengthens §IV.E,
  which is currently arguing about FP/FN trade-offs without the metrics designed
  to quantify them.

  Major (before submission):

  3. Reconcile the denoising method. The code runs bilateral filtering; the
  paper says Non-Local Means. The cheap, honest fix is to correct the text to
  "bilateral filtering," update the Buades 2005 citation, fix the "unlike local
  filters" sentence, and relabel Table 1's parameters — the empirical "denoising
  is position-neutral" result is unaffected. (Re-running with a true NLM
  implementation is the alternative but is expensive and unnecessary.)
